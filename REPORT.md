## 1. Introduction
The project I built for this module is a Customer Relationship Manager (CRM) system in Java. It lets users manage customer profiles, log communications — emails, calls, and meetings — and track follow-up tasks with deadline reminders. I built two interfaces: a Command-Line Interface and a Swing-based GUI.
From the start, I wanted the code to stay manageable when things changed. I separated the system into three layers — data models, business logic controllers, and the UI — and used three design patterns: Singleton, Observer, and Factory. Each one was chosen because it solved a real problem, not just to meet the spec. Singleton kept session state consistent across both interfaces. Observer let the UI react to changes without being directly coupled to the logic layer. Factory centralised object creation so the rest of the code did not need to care about the details.
I also used GitHub Copilot throughout. This report reflects on both sides of that experience, and what implementing these patterns at real project scale actually taught me.
## 2. Analysis of AI Support in Software Development
### How AI Tools Were Used
For core implementation I avoided asking Copilot to generate complete features. Instead, I asked for examples on specific concepts, worked through them until I understood, and then applied them myself — because if something broke, I needed to fix it. I used it more directly for the two unit test files, both main files, and the README diagrams and usage guide, where the task was about formatting rather than logic.
### Benefits
The biggest benefit was exposure to things I would not have found on my own within the project timeline. Through Copilot I properly encountered lambda expressions, the Stream API, and Swing components like JSplitPane and JTabbedPane for the first time. What mattered was not just being able to use them, but actually understanding what they were and what problems they solve. That kind of understanding is harder to get from documentation alone, because documentation tells you what something does but rarely why you would reach for it. Speed also helped for the mechanical parts. Copilot handling the CLI menu loop, JOptionPane dialogs, and boilerplate methods meant I could spend more attention on decisions that required real thought.
### Challenges and Limitations
The most instructive problem was a silent assertion bug. Copilot generated test code using Java’s built-in assert keyword, which only fires if the JVM runs with -ea. Without that flag, every assertion silently passes. I replaced them all with a custom assertTrue method that throws a RuntimeException, so failures are always visible. Two other limitations showed up: context loss across long conversations, where Copilot would repeat or contradict earlier suggestions; and no awareness of the wider codebase, so a change in one file could quietly break something elsewhere. AI-generated content also tends to be almost right rather than exactly right, which meant multiple rounds of revision.
### Overall Impact on Learning
Working with Copilot changed how I think about what these tools are actually for. The most valuable interactions were not where it wrote something for me, but where I asked it to explain a concept and kept pushing with follow-up questions. Because Copilot has a broad knowledge base, sustained conversations about a single concept — why streams are designed the way they are, what Observer is actually solving — produced explanations I could shape around my own understanding. That is something a search result rarely does.
But this only worked because I came in with some idea of what I was trying to do. When I started from Copilot’s output rather than my own thinking, it was harder to evaluate what it gave me and harder to know whether it was right for what I was building. The silent assertion bug is a clear example of what happens when generated code gets accepted without scrutiny. Going forward, I want to arrive with a rough idea first and use Copilot to refine it, rather than using it as a starting point. More than that, I think the most underrated use of AI is as a conversation partner for understanding — not for producing output, but for deepening the thinking that happens before anything gets written.
## 3. Analysis of Software Patterns in the Project
### How the Patterns Were Used
At first I picked these patterns because the spec pointed me toward them, but implementing each one made me understand what problem it was actually solving.
With Singleton, I initially thought it was just about limiting instances. After working with it, I realised the real point is coordination. Multiple SessionManager instances would mean a change in one would not appear in another. One shared instance means there is only one place to update.
Observer interested me because of what it puts in the middle. Before deciding, I compared it with direct method calls. A direct call connects one object to another — if either side changes, the link breaks. What I found interesting about Observer is that it puts an event in the middle instead. MainCLI and MainGUI do not connect to CustomerManagement directly; they both connect to a notification. Neither side knows about the other. I came to think of this as a kind of protocol — CustomerManagement publishes to it, the UI components subscribe to it, and they just get on with their own jobs. The connection does not break because there was never a direct connection in the first place.
Factory became necessary once the number of objects grew large enough that tracking how each one was created felt unmanageable. EntityFactory made that explicit — one place where all the blueprints live, rather than scattered across the codebase. It felt like the difference between correcting a blueprint and correcting every building made from it. I had initially thought of it as linear: pass in a type, get back an object. But Factory can have branching logic, conditional creation, even recursive structures. The switch in createLogger() was enough for this project, but in a larger system the factory itself could become complex enough to need its own design.
### Challenges and Limitations
Singleton’s risk is that if it takes on too much responsibility, it becomes something everything depends on but nothing can replace. In testing, this is a real problem — because the instance persists, state from one test can carry over into the next, causing failures that are random and very hard to reproduce. I kept SessionManager narrow to avoid this, but it made me aware of how quickly things can go wrong if you are not careful about what a Singleton is allowed to do.
Observer surprised me more. I assumed that dynamic connections meant inconsistencies in how I wrote the observers would not matter. I was wrong. With direct calls, inconsistent code fails immediately and tells you where. With Observer, inconsistent subscriptions fail silently, which caused me real difficulty during debugging.
### Overall Impact on Project
What this project made me realise is that no pattern is always the right answer. The real question is not which one is best, but which one’s weaknesses your project does not care about. Observer’s silent failures matter less when subscriptions are set up once and never touched again. Singleton’s shared state problem matters less when the object stays small and focused. Factory’s centralisation only pays off when the codebase is large enough to need it. In each case, the pattern worked not because it was perfect, but because its limitations happened not to matter here. Before this, I think I would have looked for the correct pattern and applied it. Now I think the preparation — figuring out what a project actually needs and which trade-offs it can live with — is more important than the implementation itself. That is probably what I will spend more time on going forward.
## 4. Ethical and Legal Considerations
### 4.1 Ethical Concerns Related to AI Use
The thing I worried about most was over-reliance. There were moments where I just wanted to paste whatever Copilot gave me and move on — and the silent assertion bug was what happened when I did. Academic integrity is harder to draw a line on. The spec allowed AI use, so nothing was wrong. But I found it hard to tell where “AI helped me” ended and “AI did it for me” began. What I tried to keep was the actual decisions: what to build, which patterns, how things connect. Whether that balance was always right, I am still not sure.
### 4.2 Data Handling and Privacy
The system holds names, ages, genders, phone numbers, emails, and addresses. Right now everything lives in memory and disappears when the app closes, so the risk is low for a prototype. That said, phone numbers are stored as plain long values, meaning they can show up in logs without anyone intending it. A small wrapper controlling how they print would be better. If this ever had persistent storage, GDPR would need to be built in from the start.
### 4.3 Broader Ethical and Legal Implications
A CRM can easily be misused — the same features that help track customer interactions can be used to monitor someone without their knowledge. Being a student project does not mean the design does not matter; the habits stick. The GUI also has no screen reader support or keyboard navigation, which would need to be addressed under the Equality Act 2010 in a real product. On licensing, I only used the Java standard library, though Copilot being trained on public repositories leaves an open question about whether generated code carries any licence conditions from that data (Freedman, 2023).
## 5. Conclusion
Before this project, I imagined learning like trying to see to the bottom of a lake — the knowledge is all down there, but too deep and too wide to take in at once. What this project taught me is that you do not need to see the bottom. Each project is like a small submarine: it takes you deep into a specific part, and even if the light only reaches so far, you get real depth in that area. That feels more useful than trying to survey the whole surface.
The AI tools were part of that light. Copilot introduced me to things I would not have gone looking for on my own — lambda expressions, the Stream API, Swing components, the finer points of each design pattern. And there was a genuine feeling of uncovering something, the sense that I had lifted a corner of something much larger. That is not nothing.
What I am taking away is that I am probably not a knowledge-first learner. I do not think I need to map every island before I set sail. What works better for me is being task-driven: start moving, notice what is missing, stop and fill in that part of the knowledge network until it is good enough to move forward. The gaps show themselves naturally, and you just have to be willing to stop when they do. And when I stop, that is where AI becomes most useful — not to generate something, but to talk through what I do not understand yet. Explaining my understanding back to Copilot and asking it to push back is close to the Feynman technique (Reyes et al., 2021): teach it, get corrected, understand it better. The difference is that AI is always available and does not get impatient.
If I were doing this project again, I would spend more time at the start thinking through the trade-offs of each design choice before writing any code. Not because the patterns turned out wrong, but because I had to learn what they were really for by running into their limits. Going in with more of that thinking done would have saved some debugging time, especially with Observer.
